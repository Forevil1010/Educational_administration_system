# 成员 A：AI 辅助与纠错记录

## 1. 选课事务 Prompt

请为高校教学管理系统编写成员 A 的学生与选课模块。技术栈为 JDK 17、MySQL 8.x 和原生 JDBC，不使用 Spring。学生表和选课表由 A 创建，教学班由另一成员创建。要求实现学生 CRUD，以及选课、退课事务。选课必须检查容量、防止重复并在失败时回滚；需要考虑两个学生同时抢最后一个名额的情况。请给出 DAO、Service 和 SQL，并解释并发安全依据。

## 2. AI 生成的不合理初稿（未采用）

模型在方案比较阶段给出过如下简化思路：

1. 开启事务。
2. `SELECT COUNT(*) FROM enrollment WHERE teaching_class_id = ?` 查询选课人数。
3. 如果人数小于容量，则执行 `INSERT`。
4. 插入前再通过一次 `SELECT` 判断是否重复。
5. 异常时回滚。

该初稿虽然出现了 `commit` 和 `rollback`，但不能保证并发安全：两个事务可能同时查到“还剩一个名额”，随后都插入，使最终人数超过容量。只查询一次是否重复也无法阻止两个并发事务同时插入相同学生和教学班。此外，初稿把退课直接写成 `DELETE`，会丢失退课历史。

## 3. 问题分析与修正

### 容量竞争

修正为在事务内执行：

`SELECT capacity FROM teaching_class WHERE teaching_class_id = ? FOR UPDATE`

同一教学班的选课事务先锁定教学班行，再统计“已选”人数。遵循同一锁顺序的事务会串行完成容量检查和写入，避免超额录取。

### 重复选课

增加数据库唯一约束：

`UNIQUE(student_id, teaching_class_id)`

Service 仍会提前检查并给出中文业务提示，唯一约束作为最后的并发防线，不能只依赖 Java 查询。

### 退课历史

将物理删除改为把状态从“已选”更新为“已退”。重新选课时恢复原记录并复用选课号，不绕过唯一约束。

### 回滚与资源关闭

选课和退课均在 `try-with-resources` 中管理 Connection，关闭自动提交，成功时 `commit`，捕获 SQL 或业务异常时 `rollback`。如果回滚本身失败，将异常添加为 suppressed exception，避免覆盖最初错误。
